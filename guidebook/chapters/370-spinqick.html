Why you need this

QICK was developed mainly by and for superconducting-qubit groups. HRL Laboratories' spinQICK adds what gate-defined spin qubits need: charge-stability scans, Pauli-blockade readout set-up, single-spin and exchange-only control, exchange calibration, crosstalk compensation, and a configuration system for many gates. Even if your hardware differs from HRL's, its code is the best public reference for how spin-qubit experiments map onto QICK. This chapter describes spinQICK, how a QICK board is run remotely from a lab PC, and how it fits with other lab software .

What spinQICK is

spinQICK (version 3.0.0 at the time of writing) is "an open-source extension to QICK designed to control electrostatically confined solid-state spin-qubits", built on QICK's tProc v2 API and some custom low-level QICK assembly . Its experiments cover:

Its demo notebooks walk through configuration, DC voltage source set-up, charge stability, crosstalk compensation, PSB, coherent LD control and coherent EO control .

Structure

  • core: pulse construction for LD and EO qubits, readout utilities, the dot_experiment base class, data handling.
  • experiments: the user-facing experiments listed above.
  • qick_code_v2: the QICK programs (tProc v2) underneath each experiment.
  • models: Pydantic models for hardware and experiment configuration, giving type-checked parameters for every gate and qubit.
  • helper_functions, backends: file management, hardware maps, plotting, analysis, and data back-ends including netCDF4 and QCoDeS.

Hardware it expects

spinQICK targets the ZCU216 (16 DAC outputs), with TI LMH5401 DC-coupled differential amplifiers on the DACs, an LMH6401 variable-gain amplifier for the ADC, optional THS3491 amplifiers, a PMOD level shifter for triggers, and a precision DC source such as a QDevil QDAC or Basel LNHR. Alternatively, Real Digital's QICK Box with "DC Out" and "DC In" modules provides the DC-coupled front end . Its recommended firmware is a ZCU216 tProc v2 build with 16 full-speed outputs and 11-channel crosstalk compensation, which needs HRL's fork of QICK and the XtalkSoc class .

On the 4x2

spinQICK is not written for the 4x2, and most of its experiments assume DC-coupled baseband outputs on many gates. What you can reuse on a 4x2:

  • its structure and configuration models, as a template for your own code;
  • its readout and analysis code (histograms, thresholds, noise measurements), which only need a readout channel;
  • its QICK programs as worked examples of PSB, Rabi, Ramsey, echo and AllXY sequences, adapted to two generators plus an external AWG for plunger pulses;
  • everything, if you move to a ZCU216 or a QICK Box later.

Running QICK remotely with Pyro4

In most labs the analysis, plotting and instrument control run on a lab PC, not on the board. QICK supports this with Pyro4 (Python Remote Objects): a name server runs on the PC (or the board), a QICK server runs on the board and publishes the QickSoc, and clients on the PC obtain a proxy object and a copy of the board's configuration :

# on the PC: start a name server
#   python -m Pyro4.naming -n 0.0.0.0 -p 8888
# on the board (in a notebook or service):
from qick.pyro import start_server
start_server(ns_host='<pc-ip>', ns_port=8888, proxy_name='rfsoc4x2')
# on the PC (client):
from qick.pyro import make_proxy
soc, soccfg = make_proxy(ns_host='<pc-ip>', ns_port=8888, proxy_name='rfsoc4x2')
prog = MyExperiment(soccfg, reps=1000, final_delay=10, cfg=cfg)   # compiled on the PC
data = prog.acquire(soc)                                         # run on the board

Programs are compiled on the PC using the configuration copy and executed on the board. The QICK team distinguishes Pyro4 (software, over Ethernet, flexible) from XCOM (hardware, low-latency links between boards) . spinQICK's documentation shows the same pattern with XtalkSoc for its crosstalk firmware .

Fitting into lab software

  • QCoDeS (Python measurement framework from Copenhagen/Microsoft) is widely used in spin-qubit labs for instrument drivers and data storage; spinQICK includes a QCoDeS data back-end . A QICK board can be wrapped as a QCoDeS instrument or used alongside one that controls your DC sources and magnet.
  • Qibolab / Qibosoq: an open-source stack that drives QICK boards as part of a hybrid quantum operating system, with calibration routines in Qibocal .
  • Your own scripts: many groups write thin Python classes that combine a DC-source driver, the QICK proxy and a data-saving layer. Start simple, and save the full configuration (including calibrations) with every dataset.
Common mistake

Mixing library versions between the PC client and the board server. Pyro sends compiled programs and configuration objects between the two; different QICK versions can produce subtle errors. Pin the same QICK version on both, as spinQICK does by pinning qick[full]==0.2.436 .

Check yourself

1. Which spinQICK capabilities depend on DC-coupled baseband outputs and therefore would not work on a stock 4x2?

Show answer
Anything that pulses gates to charge-state points: baseband gate-vs-gate scans, PSB readout pulses (measurement and idle windows), exchange pulses and EO control, LD sequences that move between load/manipulate/readout points, and crosstalk-compensated virtual pulses.

2. In a Pyro4 setup, where is a program compiled and where does it run?

Show answer
Compiled on the PC using a copy of the board's configuration (soccfg); executed on the board by the QICK server through the proxy soc.
Summary
  • spinQICK (HRL) extends QICK with spin-qubit tune-up, PSB readout, LD and EO control, exchange calibration, crosstalk compensation and typed configuration.
  • It targets a ZCU216 (or QICK Box) with DC-coupled amplifiers; on a 4x2 its readout, analysis and program structure are reusable references.
  • Pyro4 runs QICK remotely: name server, board server, PC client; pin library versions.
  • QICK integrates with QCoDeS, Qibolab/Qibosoq and custom lab code.
