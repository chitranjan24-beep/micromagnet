Why you need this

The RFSoC is a system-on-chip: a full computer (ARM processors, memory controller, Ethernet, USB) and an FPGA on the same piece of silicon, talking to each other through standard on-chip buses. When your Python code writes a QICK program to the tProcessor, or reads back a buffer of I/Q values, it travels across these buses. Knowing how they work explains where data-transfer limits come from, why some operations are fast and others slow, and what the terms in QICK's and PYNQ's documentation ("AXI-Lite register", "DMA", "MMIO", "AXI-Stream") mean.

Two halves of one chip

The processing system (PS)

The processing system contains four ARM Cortex-A53 application cores (QICK's 4x2 firmware sets them to 1.2 GHz ), two Cortex-R5F real-time cores, a DDR4 memory controller and the usual computer peripherals. On the 4x2 it boots Linux from the micro-SD card and runs PYNQ and Jupyter. The PS is a normal (if modest) computer: running Python on it is convenient but not fast, which is why heavy analysis is usually done on your lab PC.

The programmable logic (PL)

The programmable logic is the FPGA fabric of Chapter 24 plus hardened blocks: the RF-ADCs and RF-DACs, SD-FEC decoders, high-speed transceivers and Ethernet MACs. On the 4x2, the PL also has its own 4 GB of DDR4 memory, which QICK uses as a long capture buffer .

AXI: how the halves talk

All communication between PS and PL, and between blocks inside the PL, uses ARM's AMBA AXI protocols. Three flavours matter:

ProtocolUsed forExample in QICK
AXI4-LiteReading and writing individual 32-bit registers at memory addresses ("memory-mapped I/O")Setting a readout's frequency register, starting the tProcessor
AXI4 (full)Burst transfers to and from memoryDMA engines copying buffers to PS DDR4
AXI4-StreamContinuous one-way data flow, no addressesADC samples into readouts; tProcessor commands to generators; generator samples to DACs

The valid/ready handshake

AXI4-Stream (and the channels of AXI4) move data with a simple handshake: the sender raises TVALID when it has data; the receiver raises TREADY when it can accept; a transfer happens on every clock edge where both are high. This lets fast and slow blocks connect safely: a receiver that is busy just holds TREADY low.

Memory-mapped I/O and DMA

From Linux, PL registers appear at physical addresses. PYNQ's MMIO class lets Python read and write them like elements of an array (Chapter 32). Each access takes of order a microsecond from Python, fine for configuration but far too slow for moving data.

For bulk data, a DMA (direct memory access) engine in the PL copies blocks of data between a stream and PS memory by itself, at hundreds of MB/s to GB/s, while the CPU waits or does other work. QICK uses DMA engines to load programs into the tProcessor, upload waveform envelopes into generators, and read back readout buffers . PYNQ allocates the contiguous memory buffers DMA needs.

Worked example: data rates

One readout returns one complex I/Q pair (two 32-bit integers, 8 bytes) per shot. 16 384 shots make 128 KiB, transferred by DMA in well under a millisecond. Raw ADC data is another story: 4423.68 MSPS × 2 bytes = 8.8 GB/s per channel. No PS–PL path can stream that continuously to Linux, which is why decimation and accumulation must happen in the PL, and why the long DDR4 capture buffer sits on the PL side.

Interrupts and timing

The PL can signal the PS with interrupts (for example "buffer full"), but Linux's response time is microseconds to milliseconds and not deterministic. Anything that must happen at a precise time, such as a pulse after a measurement, must therefore be done in the PL. That is the design principle behind QICK: the PS prepares and collects, the PL acts in real time.

On the 4x2
  • PS: quad Cortex-A53, 4 GB DDR4, Gigabit Ethernet, USB 3.0, micro-SD, Mini DisplayPort .
  • PL: 8 RF-ADCs and 8 RF-DACs on the chip (4 ADCs and 2 DACs wired to SMA connectors), 4 GB PL DDR4, a QSFP28 cage for up to 100 Gb/s Ethernet, PMOD and SYZYGY connectors .
  • The 100G QSFP28 port could stream large amounts of data to a PC, but QICK's standard firmware does not use it; data reaches the PC through the PS and Gigabit Ethernet.
Check yourself

1. Why can't the tProcessor be replaced by a Python loop on the ARM cores?

Show answer
Linux and Python give no timing guarantees: interrupts, scheduling and garbage collection cause delays of microseconds to milliseconds, and each register access takes about a microsecond. Pulses need nanosecond-precise, deterministic timing, which only logic in the PL provides.

2. What is the difference between AXI4-Lite and AXI4-Stream?

Show answer
AXI4-Lite reads and writes single registers at addresses (control). AXI4-Stream moves a continuous flow of data from one block to the next without addresses (data paths such as ADC samples).
Summary
  • The RFSoC combines a processing system (ARM cores, DDR4, peripherals, Linux) with programmable logic (fabric, RF converters, hardened blocks).
  • AXI4-Lite carries register accesses, AXI4 burst transfers, AXI4-Stream continuous data, all with a valid/ready handshake.
  • MMIO is for configuration; DMA is for bulk data; real-time actions must be in the PL.
  • GSPS raw data cannot be streamed to Linux, so QICK reduces it in the PL.
